# 機器Logicの分割と実装ルール

この文書は、Input・State・Outputを持つ機器のLogicを、工程ごとに分割するときの共通ルールを定める。ATCで決めた構成を一般化したものであり、新しい機器の実装や既存機器の整理に使用する。

基本の責務、依存方向、更新ライフサイクルは [ImplementationRules.md](ImplementationRules.md) に従う。機器ごとの処理順、判定条件、故障時の動作は各機器の仕様書で定める。ATCの具体的な工程と条件は [TrainAtcProcessingFlow.md](../Train/Atc/TrainAtcProcessingFlow.md) を参照する。

## 1. 構成と命名

以下の名前にある `<機器名>` と `<工程名>` は、対象機器と担当工程の名前に置き換える。

| 種類 | 名前 | 責務 |
| --- | --- | --- |
| Context | `<機器名>Context` | Input・Settings・State・Outputなどの実行時データをまとめる |
| Input | `<機器名>Input` | 1ステップ分の入力スナップショット |
| 全体State | `<機器名>State` | 各工程のStateと、機器全体の状態をまとめる |
| 工程State | `<機器名><工程名>State` | 担当工程の結果と、ステップをまたいで保持する状態 |
| 親Logic | `<機器名>Logic` | 全体の工程順と、各工程の結果の集約 |
| 子Logic | `<機器名><工程名>Logic` | 担当工程の判定・計算・State更新 |
| Helper | `<機器名><工程名>Helper` | 対応する子Logic内で共通に使う計算 |
| OutputLogic | `<機器名>OutputLogic` | 確定した状態から外部向けOutputを生成する |
| Controller | `<機器名>Controller` | 外部からの入力収集、親Logicの呼び出し、Outputの反映 |

LogicはStateと同じファイル単位で分割し、対応するStateとLogicの名前を揃える。例えば、`DevicePositionState` の更新は `DevicePositionLogic` が担当する。

分割は処理の責務に合わせる。小さな機器に、名前を揃えるためだけの工程・クラス・空フォルダを追加しない。

## 2. Logicの呼び出し

- 子Logicの呼び出しは親Logicに集約する。子Logic同士で関数を呼び合わない。
- 基本的に、各子Logicに入口となるトップレベルの関数を設ける。その関数に大まかな処理の流れを上から順に記載し、詳細処理は同じクラスの補助関数へ分ける。
- 全体の工程順は親Logic、各工程内の処理順は対応する子Logicのトップレベル関数に置く。
- Logicは独立した `static class` とする。`partial` で分割しない。
- Controllerからは親Logicを呼ぶ。工程の順序をControllerや子Logicへ分散させない。
- OutputLogicも親Logicから呼び、必要なStateが確定してからOutputを生成する。

| 関数 | アクセス修飾子 |
| --- | --- |
| 親Logicの外部公開が必要な関数 | `public` |
| 親Logic内だけで使う補助関数 | `private` |
| 親Logicから呼ぶ子Logic・OutputLogicの入口 | `internal` |
| 子Logic・OutputLogic内だけで使う補助関数 | `private` |
| 対応する子Logicから呼ぶHelperの関数 | `internal` |
| Helper内だけで使う補助関数 | `private` |

アクセス修飾子だけでは呼び出し元を限定できないため、`internal` の関数でも上記の呼び出し関係を守る。

## 3. State・Input・Outputの更新担当

各子Logicが書き換えてよいStateは、自分のファイル名に対応するStateだけとする。他のStateは参照できるが、直接変更しない。他のStateが保持する配列・オブジェクトの参照を通した変更も行わない。

| 更新担当 | 書き換えてよい情報 |
| --- | --- |
| Controllerの入力収集 | Inputのスナップショット |
| 親Logic | 全体State直下の全体状態 |
| 各子Logic | 対応する工程Stateと、その中の配列・オブジェクト |
| OutputLogic | Outputのみ |

- 親Logicは子Stateを直接変更せず、担当する子Logicの入口を呼ぶ。初期化・リセットも同じ担当関係に従う。
- Inputは入力収集時に取り込み、LogicとHelperからは変更しない。計算中は同じステップのスナップショットを使用する。
- OutputはOutputLogicだけが生成する。OutputLogicはStateを書き換えず、他のLogicからもOutputを書き換えない。
- 同じ意味の情報は必ず1箇所で管理する。別工程で必要な場合は、所有するStateを参照する。
- 現在の入力と、過去の計算で採用した条件のように意味が異なる情報を保持する場合は、違いを名前やコメントで明記する。

## 4. 各工程の結果と全体状態

各工程の失敗は、担当するStateの結果、または戻り値として親Logicへ渡す。後続工程の失敗を理由に、別工程の確定結果を書き換えない。

全体の正常性や動作可否は、親Logicが各工程で確定した結果を集約して決める。集約時に入力確認を再実行せず、同じ不正判定を複数工程に重複させない。

- 入力を確認する工程、計算する工程、出力を決定する工程の責務を分ける。
- 有効な値と取得失敗を区別する。正常な値である `None`、`0`、`false` などを、取得失敗の代わりに使わない。
- 正常な無効状態と、入力欠損・計算失敗による使用不可を区別する。何を故障扱いにするかは機器ごとの仕様で定める。
- 前回結果を保持する場合は、保持条件、保持時間、解除条件を機器の仕様書に記載する。
- 生成・保持・消去などの処理方針を決める工程と、その方針に従って計算する工程を分ける場合は、方針の所有者も1箇所にする。

## 5. Helperの分割と制限

同じ子Logic内の複数の関数で共通の処理を使う場合は、対象機器の `Scripts/Helper/` に対応するHelperを作ってよい。Helperへの分割は必須ではない。

- 名前は対応するLogicの `Logic` を `Helper` へ置き換える。例えば、`DevicePositionLogic` に対応するファイルは `DevicePositionHelper.cs` とする。
- Helper内の関数はすべて `static` にする。
- Helperの引数にContextを渡さない。必要な配列・変数だけを明示的に渡す。
- Helperは原則としてState・Input・Outputを直接変更せず、引数から計算した結果を戻り値または `out` 引数で返す。渡された配列・オブジェクトを通した変更も行わない。
- 計算結果をStateへ反映する処理は、担当する子Logicに置く。
- 子Logicは自分に対応するHelperだけを使用する。別の子Logicに対応するHelperを呼ぶことは禁止する。
- HelperからLogicや別工程のHelperを呼ばず、対応する工程内の計算に責務を限定する。

例えば、`DevicePositionLogic` から `DevicePositionHelper` は呼べるが、`DevicePatternLogic` から `DevicePositionHelper` は呼べない。

## 6. 文法・改行・コメント

- `if`・`else`・`for`・`foreach`・`while` などのブロックは、処理が一つだけでも `{}` と改行を省略しない。
- 条件と処理を一行に詰め込まず、開始・終了の波括弧を別行に置く。
- 処理単位で空行を入れ、入力確認、計算、結果反映などの区切りを読み取れるようにする。
- 複雑な計算や分岐には、目的、条件の理由、前提が分かるコメントを適宜入れる。
- トップレベルの関数を読むだけで、その工程の大まかな処理順が分かる構成にする。
- 関数名は処理内容と一致させる。使用可否の判定とパターン生成など、異なる責務を一つの名前に隠さない。

## 7. 機器ごとの仕様書に記載する内容

この共通ルールに加え、実装前に対象機器の仕様書へ以下を記載する。

- 工程の実行順と、各工程の入口関数。
- 各工程が参照するInput・Settings・Stateと、更新するState。
- 各情報の所有者と、保持・初期化・リセット条件。
- 入力欠損、計算失敗、正常な無効状態の扱い。
- 全体状態を集約する条件と、Outputへの変換条件。

機器固有のモード、タイマー、制御条件はこの文書へ追加せず、対象機器の仕様書で管理する。
