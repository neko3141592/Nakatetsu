# 線形作成方式の調査：BVE・OpenBVEと旧TD-ATC

採用結果：オフセット方式を継続する。本文の独立線形案は比較用の未採用案。走行基準の先行移植は [GuideLine移植記録](GuideLineMigration.md) を参照。

調査日：2026-09-07。目的は、分岐付帯曲線を作成しやすくするため、線形の入力方法と実行時の表現を見直すこと。
追加調査：[Open Rails・Transport Fever 2の線路グラフ](TrackGraphSimulatorResearch.md)。接続グラフ・形状・作成入力を分ける実例を整理した。
公式マップ仕様と開発者の解説を調査した。BVE内部の非公開実装や数値積分方式を確認したものではない。新側のコード変更・BVE上の実走検証は行っていない。

## 1. 調査結果

### BVE：走行する線路は半径、他軌道は相対位置で指定

BVEの自軌道は距離程ごとに `Curve.Begin` / `Curve.End` などで曲線を指定できる。他軌道は `Track[key].X.Interpolate` で自軌道からの横位置と相対半径を指定する。したがって「全線路が独立した線形を持つネットワーク」とは異なる入力モデルである。半径の意味を自軌道と他軌道で取り違えない。[公式マップ仕様](https://bvets.net/jp/edit/formats/route/map.html)

開発者は、曲線を区間の開始・終了で書く方式と、補間点で書く方式を併用できると説明している。参考になるのは、計算内部のパラメーターをすべて入力者に渡すのではなく、用途に応じた記述方法を用意している点である。[開発者による構文解説](https://mackoy.exblog.jp/23325011/)

### OpenBVE：主軌道基準の制約が残る

CSV形式の `Track.Curve` は主軌道の曲率を指定し、他軌道の `Track.Rail` は主軌道からの位置を指定する。線路形状の指定と、配置するレールオブジェクトの選択は別に存在する。[公式CSV仕様](https://openbve-project.net/documentation/HTML/route_csv.html)

OpenBVEには `Track.Switch` 等の分岐機能があるが、公式ページは主軌道Rail 0中心の形式による制約を説明し、副軌道上の信号・速度制限等について限定的な実装と記載している。これは参照ページの説明であり、あらゆる最新ビルドの挙動を検証した結論ではない。[公式分岐仕様](https://openbve-project.net/documentation_hugo/en/routes/xml/switches.html)

**考察：BVE系の入力は参考になるが、任意の経路を走るTD-ATCの内部構造までそのまま合わせる理由にはならない。** 線路の作成方法と、走行可能な接続グラフは別に設計する。

## 2. 旧方式で描きづらくなる理由

以下は旧 `TrackOffsetSegment.cs` と `TrackRuntimeResolver.cs` の読解に基づく。

1. **引きたい線路の距離ではなく、基準線へ投影した距離で区間を指定する。** `baseLengthM` は分岐先の実際の走行距離ではない。
2. **Arcの半径は相対座標上のもの。** 基準線が曲がると、実際の線路の半径としてそのまま解釈できない。
3. **開始位置・開始角・区間長・終点位置の整合を作成者が考える必要がある。** 「この分岐出口から、向こうの直線へ半径Rで接続したい」という入力になっていない。
4. **Cubicは任意の端点接線を指定できない。** 実装は名前に反して5次のsmoothstepであり、両端の相対傾きが0になる。角度を持つ分岐出口からそのまま繋ぐ用途には合わない。
5. **Arcは基準線方向へ進む一価の表現を使う。** 開始角の絶対値90度未満などの条件があり、大きく向きの違う線路を1つの基準線で表し続けるのには制約がある。

直線の基準線上での旧Arc計算は、概ね次の関係を使う。

```text
基準方向への進み = R × (sin(終端角) - sin(開始角))
横位置の変化     = R × (cos(開始角) - cos(終端角))
```

つまり、半径・開始角・進みを決めれば終点は決まる。さらに終点座標も任意に固定すると、条件が矛盾することがある。旧コンパイラーには整合性の検査があるが、欲しい接続形状を逆算して候補を提示する作図機能ではない。

また、旧方式でも別の `TrackGeometry` を作り、オフセット0のEdgeを載せれば独立した線形を表す余地はある。新しい型を増やす前に、この方法で分岐出口を起点に生成できるか試す価値がある。ただし端点を合わせる操作や、曲線近似の精度は別途必要になる。

## 3. 新側への提案：作成方法を複数用意する

| 作りたいもの | 入力方式の提案 |
| --- | --- |
| 単純な並行線 | 基準線からの一定オフセット |
| 軌道間隔の変化 | 始終点の横位置と接線条件から生成 |
| 分岐器とその出口 | 形式・寸法に基づくテンプレートで、入口・出口の位置と向きを生成 |
| 分岐付帯曲線 | 分岐出口の位置・向きから、直線・円曲線・必要な緩和曲線を連結 |
| 既存線へ接続する曲線 | 接続先の位置・向きと、指定半径等から候補を求める |
| 旧路線 | 旧JSONのオフセット方式をそのまま読み込む |

これはTD-ATCへの設計提案であり、BVEがこのテンプレート・接続計算機能を備えているという意味ではない。

分岐器自体と、その先の付帯曲線も区別する。分岐器テンプレートが返す「出口の位置・向き」を次の曲線の始点にすれば、作成者が毎回基準線に対する角度・横位置を計算し直さずに済む。分岐器の具体的な寸法は使う形式の資料から定義し、番数だけから実寸を決めつけない。

内部は、どの作成方法でもEdge上の距離から位置・姿勢を取得できる共通の評価口へ揃える。

```text
旧オフセット入力 ─┐
独立した線形入力 ─┼→ 検証・コンパイル → Edgeの形状 → 距離から位置・姿勢
分岐テンプレート ─┘                         ↑
                                    接続関係はNode/Graph
```

毎フレーム接続曲線を解くのではなく、編集・コンパイル時に作成して検証する。距離表が必要な形状ではそこで生成する。実行時は選択済みの形状を評価する。

「独立線形を既存Geometryの機能で実現する」か「別の形状型を設ける」かは小さな試作で決める。直ちに汎用Splineや大規模なEditorを導入する必要はない。

## 4. 接続ツールで決める必要があること

最初のツールは「始点位置・始点方向・半径・曲線長または曲がる角度」から終点を生成するものとする。次に、既存の直線等へ接続する機能を追加する。

始終点位置・始終点方向・半径をすべて固定しても、必ず円弧1本で繋がるわけではない。解がない場合はエラーとし、半径・直線長・曲線構成のどれを変更可能にするか明示する。勝手に半径を変えて見た目だけ繋げない。

検証する項目：

- 位置が一致するか。
- 接線の向きが一致するか。
- 必要な場所で曲率が連続するか。分岐器境界等では形式に応じて扱う。
- 指定した半径・曲線長が実際に得られているか。
- 勾配・カント・高さが整合するか。
- 線路の接続を変更したとき、依存する曲線の再生成が必要と分かるか。

## 5. 移植計画への変更

旧数式の互換性確認と、新しい作成方式の採用を分ける。従来計画の「最初に旧方式を移す」を「最初に共通の位置評価口を決め、旧方式と独立線形の小さな比較をする」に修正する。

最初の比較ケースは以下とする。

1. 直線から角度を持って出た出口へ、一定半径の曲線を追加する。
2. その曲線を隣接する直線へ接線が合うよう接続する。
3. 基準線が曲がっている場所でも、指定した実半径を維持できるか確認する。

これで入力項目数、手計算の必要性、接続誤差、実半径の再現性を比較する。**旧データを読めることと、新規線路を旧JSONの書き方で作り続けることは分けて考える。**
