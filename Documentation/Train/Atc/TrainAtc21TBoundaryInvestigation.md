# 21T進入時のATC非常作動の調査

2026-10-04、Unity 6.4（6000.4.0f1）のNtLine SceneをPlayして調査した。

原因は、受信機が電文を受け取った時点より、車上ATCの保持位置が先に進むことである。20Tの有効電文に対して21Tのキーを要求し、パターンを消去して非常を保持する瞬間を実測した。

## 実測条件

- 保存済みNtLine Scene、tick幅0.015秒。
- 初期先頭車中心400m、前側受信機は中心から前方8m。
- 前側運転台を準備し、非常位置で入力を安定させた後、Nを経て力行する。
- 21T-2RTを要求して開通させる。Scene・Prefab・設定Assetは変更しない。
- UnityのPlay中にApplicationSimulationControllerを一時停止し、StepOnceで通常の全tick処理を進める。描画間隔やPlaybackSpeedに依存せず、各tickのATC計算直前・直後を記録する。
- 運転中のEB装置の無操作作動を混同しないため、診断側から定期的にリセット操作を入力する。

一時的な診断フックで前後の位置、前後受信電文のキー、入力の有効性、進路状態、パターン、非常要求と保持を記録した。常用・非常の判定処理自体は変更していない。比較走行だけ移動距離の積分方法を切り替えた。

## 非常になったtick

[P3の実測記録](Diagnostics/2026-10-04-21T/original-P3-emergency.tsv)で、tick 4108に失敗した。

| --- | ---: | ---: | ---: |
| 受信機の物理位置[m] | 999.6474 | 999.9583 | 1000.269 |
| ATC更新後の位置[m] | 999.8033 | 1000.1141265 | 1000.4247194 |
| 受信電文の対象 | 20T | 20T | 21T |
| ATCが要求したEdge | 20T | 21T | 21T |
| 電文キー一致 | true | false | true |
| 常用パターンのサンプル数 | 281 | 0 | 81 |
| パターン有効 | true | false | true |
| 非常要求 | false | true | false |
| 非常保持 | false | true | true |

21Tの入口は物理距離1000mである。tick 4108の測定速度は20.71879m/s（約74.6km/h）。受信機は入口の約4.2cm手前だが、ATCは入口の約11.4cm先へ進み、両者に約15.6cmの差がある。

このtickでも、位置既知・isHealthy・ATC有効・電文有効・ブレーキ設定取得・速度測定取得・車両質量取得はすべてtrueである。21T-2RTのProceedAllowed・PathEstablished・RouteLockedもtrue、CancelPendingはfalseであった。後側の位置更新にも失敗していない。

## コード上の因果関係

1. TrainSimulationController.Calculateは、現在の物理速度と位置からSpeedSensor・受信機を更新した後、車上ATCを計算する。新しい物理移動と線路位置の更新はその後に行う。
2. TrainAtcLogic.UpdateAtcEdgePositionは、受け取った現在速度に今回のdtを掛けて、受信機の位置より先へ保持位置を更新する。
3. 20T→21Tの境界には接続先が一つしかないため、位置更新は正常に21Tへ進む。isPositionKnownはtrueのままである。
4. 軌道回路ごとの電文の辞書には、その回路内のATC Edgeのキーだけが入る。20Tの進路情報のpathに21Tが含まれていても、20T電文に21Tの辞書キーはない。
5. UpdateBrakePatternの電文キー取得に失敗し、ClearBrakePatternを呼ぶ。
6. HasEmergencyBrakeCauseもパターン位置を取得できずtrueとなり、UpdateBrakeOutputがisEmergencyHoldをtrueにする。
7. 次tickには受信機も21Tへ入り、電文・パターン・非常要求は正常へ戻る。走行中なので「原因解消・停止・マスコン非常位置」の解除条件を満たさず、非常保持だけが残る。

位置の問題は、単にUpdateAtcEdgePositionとCaptureCurrentTelegramの呼び出しを入れ替えても解消しない。受信電文と照合する位置の時刻を揃える必要がある。

元のP4でも、入口付近で約16cmの先行を確認した。この回は受信機とATCが同じtickで境界を跨いだため、辞書キーが一致した。P3では跨ぐtickが分かれて失敗した。P3というノッチそのものを異常原因にする根拠ではなく、境界を跨ぐ時刻の違いで発生した結果である。

比較走行では、初回測定は速度を保存するだけとし、以後の移動距離を次の式へ一時的に変更した。

```text
移動距離 = 0.5 ×（前回測定速度 + 今回測定速度）× 前回tick幅
```

物理受信機999.9583m・測定速度20.71879m/sの地点で、ATC位置も999.9583mになり、20Tキーとの照合に成功した。その次tickで両者が21Tへ切り替わり、非常保持も発生しなかった。各条件1回の比較であり、全境界・全運転条件の修正検証ではない。

## 現示が消える経路と確認範囲

失敗tickのATC Output.hasValidPattern=falseを確認した。TrainAtcTimsDisplayAdapterはTIMSの収集時にこの値を読むと、HasValidPatternをfalseにし、PatternAllowSpeedKmhなどのタグを削除する。TimsSpeedMeterは有効フラグまたは速度タグが取得できなければ、点灯する三角現示を消す。

ただし、TIMS MasterBusの収集は0.25秒周期であり、1tickだけのパターン無効を拾うかは収集時刻による。非常を再現したP3の最初の記録にはMasterBus値を含めていないため、その試行で画面の三角が実際に消える瞬間までは特定していない。追加のP1・P2・比較P3ではMasterBus値も記録したが、これらの走行ではパターン無効が発生しなかった。

また、今回の失敗ではisHealthy=trueであり、ATC/HasFaultの故障ランプ点灯とは区別する。以前の故障ランプや、復旧しない持続的な現示消失まで同じ原因と断定する記録ではない。

## 対処案

まず、位置積分を「前回受信から今回受信までの移動」へ変更し、今回の電文と同じ時点の位置で照合する。初回測定、dt=0、初期化・明示的補正、速度取得失敗時の履歴処理も併せて定義する。

台形積分だけで境界の厳密一致が保証されるわけではない。物理側は先頭車中心のfloat位置へ変位を加算し、受信機位置を取り付け位置から求める。ATC側は受信機位置を別に累積し、ATC Edgeを跨ぐと局所距離へ戻るため、floatの丸めが一致しない。物理の停止tickでは停止時刻まで移動を切り詰める処理もある。

残る微小な差には、有効電文のキー・進行方向・隣接Edgeの連続性を確認した上で境界位置を補正するなど、境界の整合方法を併せて検討する。照合失敗を一律に無視したり、無信号で前回電文を残す対処にはしない。

調査後、一時的な診断フックと比較用の変更を削除し、TrainAtcController・TrainAtcLogicは調査開始前の内容と完全一致することを確認した。現在の制御コードには修正を入れていない。
