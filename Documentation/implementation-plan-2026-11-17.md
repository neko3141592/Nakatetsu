## 1. 到達方針

駅一覧の確認により、今回の制作範囲を中鉄中央（NT01）〜猿沼（NT11）、11駅・営業キロ10.6kmに確定した。[駅一覧・種別別速度・残件](Track/NtLine/NtLineSpecification.md)を参照。

**仮シナリオよりCTC／PRCの開発を優先する。手動CTC→列車追跡・試験ダイヤ→PRC→NPC・2列車運行の検証→全線運行→snapshot→本番シナリオ・ゲーム進行の順で進める。** 10/11は手動CTC・列車追跡の最小構成、10/18は試験線でPRCによる2列車運行の成立を当面の目標とする。

11/17の完成目標、11/8の完成候補、11/9以降の不具合修正・配布確認期間は維持する。ただし、当初の「10/18全線運行・11/1に3シナリオ」は順序変更前の目標であり、CTC／PRCの残工数を見積もったうえで後続工程の日付を再設定する。優先順位の変更だけで当初日程を維持できるとは扱わない。

走行・占有・連動・地上／車上ATCは実装済みで、2026-10-08に本人から信号装置類の完成報告がある。次はこの保安基盤にCTCの列車追跡・手動集中制御とPRCの自動進路要求を接続する。仮の選択→運転→完了画面は先に作らず、snapshot完成後の本番ゲーム進行へまとめる。NPCに必要な停止位置・停車判定・戸扱い・発車条件は先行して実装する。

この計画は**Codexでコード作成・テスト・データ制作補助を進め、人間が仕様判断・Unity統合・試運転を担う、やや攻めた見積もり**である。週20〜25時間なら無条件で間に合う、という保証ではない。10/11・10/18のCTC／PRCの到達判定で残工数を確認し、景観の作り込みと運行の複雑さを早めに削る。

### 初期調査時の注意点（W1で対応済みの項目を含む）

1. **100m線形では現行編成を収められない。** `Consist.asset` は20m車×10両で約200m。単車試験の次に、500m以上の線路と全編成を載せられる初期位置を用意する。
2. **時間進行を早期に外から呼べるようにする。** 現在は `TrainSimulationController.Update()` → private `Step(Time.deltaTime)`。ダイヤ時計、複数列車、早送り、snapshotを後付けすると更新順が崩れやすい。第1週で手動tick経路を設ける。
3. **文書とコードの差分がある。** 実装ルールは `ISimulationController.CollectInput()` 等を説明するが、現在のInterfaceは `Calculate` と `ApplyOutput` の2メソッド。Physicsも `SetInput()` で入力を受ける。全機器の一括改修を始めず、現行接続を確認して世界全体の更新契約を先に決める。
4. **既存の線路方針を維持する。** [線路基盤の移植計画](./Migration/TrackFoundationMigration.md) はオフセット方式採用を明記している。締切前に別方式の線路エディターを作り直さない。
5. **ATOの設計資料は実装完了を意味しない。** NPC用の簡単な自動運転は必要だが、プレイヤー用ATO/TASCの本格実装は今回の必須範囲から外す。

### 依存関係

```text
【実装済み】線形・グラフ → 編成移動・通過履歴 → 全長占有 → 連動 → 地上ATC → 車上ATC
                                                       ↑
【次の開発】手動CTC → 列車追跡・試験ダイヤ → PRCの進路要求
                             ↓                  ↑
                  停車・戸扱い・発車条件 → NPC指令
                             └────────┬─────────┘
                                      ↓
                             2列車運行の統合検証
                                      ↓
                             全線・昼1時間の運行
                                      ↓
                         運行世界のsnapshot生成・復元
                                      ↓
                    本番シナリオ選択・手動運転・完了・結果
```

手動CTCとPRCロジックは既存の1駅2線試験線で開発を始める。PRCの入力となる停車段階・発車条件は先に契約を決め、NPC完成前も試験入力で検証する。実列車の自動運行検証にはNPC・停車処理を接続する。仮シナリオの画面遷移と新規2駅の制作をCTC／PRCの前提にしない。

路線・駅の制作はCTC／PRCの運行検証後に全線へ広げる。運行確認に必要なホーム・停止目標は用意し、景観の仕上げは後続工程に置く。

## 5. 実装を膨らませないための設計方針

### 所有者と配置

以下は新規実装の配置案。既存asmdefの依存方向に従い、必要な機能を追加する時点でフォルダを作る。

| 所有者 | 責務 |
| --- | --- |
| `Track` | Geometry/Graph、分岐、経路上距離、駅・閉塞、占有、連動、地上ATC |
| `Train/Simulation` | 既存機器とPhysics、速度から移動距離への積分。Trackとの接続は適切な上位Adapterを介する |
| `Train/Equipment/Atc` | 車上ATCの入力有効性、速度パターン、制動要求 |
| `Train/Equipment/Tims` | ノッチ調停がATC Outputの制動要求を直接読み、既存指令と調停する。ATC状態の表示はBusへ接続 |
| `Application` | 世界時計、全列車の更新順、CTCの列車追跡・監視・手動操作、ダイヤとPRCの自動進路要求・待機・手動抑止、NPC指令、snapshot、シナリオ・UI |
| `World` / `Track/Presentation` | 背景、視点、線路・駅・小物の表示。運行Stateを書き換えない |

各列車が別々の `Update()` で世界時計を進めない。固定tickの例は0.02秒だが、第1週の既存機器確認で決定する。早送りはdeltaTimeを巨大化させず、同じtickを複数回実行する。

現在の世界tickは、全列車の車上制御・機器・Physics・移動→全列車の占有確定→連動→地上ATC電文→時計更新の順で進み、地上電文を次tickの車上制御へ渡す。CTC／PRCはこの契約に沿い、全列車の位置・占有が確定した後、連動の更新前に追跡・要求処理を挿入する。NPCの通常運転指令は列車更新前に準備する。イベントを確定し、時計更新後をsnapshot可能境界とする。先行列車との距離にはtick遅れも含む余裕を取る。同一tick中に列車ごとに共有占有を随時書き換えて順番依存を作らない。

列車追跡は既存Train ID・個別位置・占有の取得口を上位Adapterへ集約する。軌道回路の合算占有boolだけから列番を推測しない。連動の`TryRequestRoute`成功は予約受付までであり、転換完了・開通と区別する。連動自身は待ちキュー・自動再要求を持たないため、PRCが待機・再要求・処理済みイベント・手動抑止を管理する。

### 保安と運転の最小仕様

- ATCは「路線制限、分岐制限、停止限界までの減速パターン」の最も厳しい値を使う。0速度目標は経路距離で扱い、別線の見かけ上近い列車を誤検知しない。
- 制動パターンは実測した常用制動性能を下回る前提で設定する。応答遅れ・下り勾配・位置余裕を考慮し、最高速度で停止限界手前に止まることを試運転で確かめる。
- 無効・失効したATC情報、未検知分岐、未確保経路では力行を許可せず、規定の停止要求を出す。これらはゲーム内モデルの仕様であり、実設備規格への適合を主張しない。
- NPCは通常の運転指令として力行・常用制動を要求する。ATC介入用フィールドをNPCの通常ブレーキに流用しない。
- 初期版のNPCは同じ車両シミュレーションを使う方針で開始する。性能が不足した場合だけ簡易モデルを検討し、占有・連動・ATC・保存契約は共通にする。
- 駅停車成功は、例として速度0.1m/s未満かつ停止目標±3m以内で判定し、戸扱い・停車時間を経て発車可能にする。閾値はゲーム用の暫定設定として第6週に確定する。
- 正常な最終駅停車と必要な戸扱いで運転完了。軽微な遅延は結果に記録し、回復不能なオーバーラン・線路端逸脱などは理由を示して再挑戦できるようにする。
- 終端で複雑な折返しを組む代わりに、プレイ区間外の生成・退出区間を使える構成にする。列車全長が抜ける前に占有を消さない。プレイヤーの全線運転には終着までの有効長を確保する。

## 6. ダイヤとsnapshotの仕様

### 生成の流れ

```text
路線定義＋編成定義＋昼ダイヤ＋初期在線列車
  → ウォームアップを含む固定tick運行（全列車NPC）
  → tick確定境界で60秒ごとにsnapshotを保存
  → 検証済みsnapshot一覧
  → snapshot ID＋担当列車ID＋終了条件からシナリオを定義
  → 起動時に世界を復元し、対象列車だけ手動へ切替
```

1時間の本編を `[12:00, 13:00)` とする場合、60秒間隔なら12:00〜12:59の60件が基本となる。13:00の終端確認用を含めるなら別に1件と明記する。間隔は設定値とし、開始状況が選びづらい場合のみ30秒へ変更する。

12:00から空の路線に列車を順次出すだけでは昼ダイヤの途中状態にならない。運転開始前から在線している列車を初期定義するか、例えば11:40から運行を進めて12:00以降を保存する。必要なウォームアップ時間は全線走行時間で決める。

最後のシナリオの完了時刻＋遅延余裕まで運行データを用意する。例として12:30開始・25分運転なら12:55完了を狙う。遅延で13:00を越える場合も進路を閉じたりNPCを突然消したりせず、終端まで継続する。必要なら前後の補助ダイヤを足すが、制作の中心は昼1時間分とする。

### 保存対象

| 分類 | 保存する値 | 復元時の扱い |
| --- | --- | --- |
| 共通 | schemaVersion、route/timetable/vehicle定義のIDとハッシュ、固定tick幅、tick番号・時刻、乱数State（乱数を使う場合） | 定義不一致はロードエラーにし、無理に読まない |
| 列車 | 永続Train ID、運行ID、編成、位置基準点、Edge IDと実距離、編成向き、通過履歴、速度、次駅・停車段階・遅延 | 通過履歴から全車位置・編成全長占有を再構築 |
| 車両内部 | マスコン、ドア状態とタイマー、BC圧・モーター等の応答State、EB・非常保持、ATC内部State、必要な通信の前tick値 | 次tickの振る舞いに影響する状態を監査し、担当Logicに明示的な復元入口を設ける |
| 地上 | 分岐位置・転換途中状態、進路鎖錠・列車との対応・通過段階、未処理進路要求 | 占有だけから鎖錠状態を推測しない。保存した状態と再計算結果を照合 |
| 運行 | CTCの列車ID／列番／運行ID対応、各列車のダイヤ進捗、PRCの要求待機・処理済みイベント・手動抑止／自動制御モード、停車・発車・生成・退出のイベント消化状況、NPC制御State | 消化済みイベントや手動取消済みの要求を復元後に意図せず再実行しない |

Transform、MonoBehaviour参照、描画物、辞書キャッシュをそのまま保存しない。復元は「時計停止→定義検証→列車・機器生成→State適用→経路・占有再構築→鎖錠照合→Bus/表示更新→担当列車の操作権変更→tick開始」の順に行う。

初期版の3件は担当列車が駅停車中のsnapshotを選び、手動切替時のノッチを中立・停止保持へ安全に整える。これは明示した開始時の変更としてログに残し、他列車や地上状態を初期化し直さない。一般の生成snapshotには走行中・分岐跨ぎ列車も含まれるため、保存対象から動的状態を除外しない。

### 復元の合格条件

- 同一バージョン・同一実行環境・同一入力で、連続運行と保存復元後運行の進路・占有・イベント順が一致する。
- 位置・速度等は暫定許容値（例：位置1cm、速度0.01m/s）で比較する。誤差を許容しても、閉塞・信号の離散状態が変わるケースは不合格とする。
- 分岐跨ぎ、先行列車待ち、停車・戸開中、BC加圧中を含める。少なくとも復元後5分間を比較する。
- 別OS間のビット単位の完全一致は初期版の目標にしないが、配布先OSで3件すべての運転成立を確認する。
- snapshotは**初期状態**として使う。開始後の世界を録画のように再生しない。プレイヤーが遅延したらNPC・CTC・PRC・連動・ATCを再計算する。

## 7. 初期3シナリオ案

駅名・発時刻は第4〜6週のデータ確定時に置き換える。以下は、1時間のダイヤから成立する範囲で選ぶ制作案。

| シナリオ | snapshotの選び方 | 運転区間・目安 | 体験と検証目的 |
| --- | --- | --- | --- |
| 1. 昼間の全線各停 | 例：12:00、始発駅停車中 | 10.6km・11駅、20〜30分 | 全線が運転可能であること、基本操作、定時運転 |
| 2. 昼間の区間運転 | 例：12:15、中間駅で停車中の別列車 | 4〜6駅、10〜15分 | 途中時刻・途中位置から自然に始められること、短く遊べること |
| 3. 先行列車に続く運転 | 例：12:30、先行列車との間隔が短い駅停車時 | 4〜6駅、10〜20分 | ATCによる速度抑制、進路待ち、開通後の運転再開 |

第3シナリオ用の条件は元ダイヤの停車時分・発車間隔の中で作り、別スクリプトで信号を赤に固定して演出しない。全線走行が30分を超えそうなら、駅間時分と開始時刻を調整し、完了までの運行データを確保する。

## 10. Codex Pro 5xの使い方

公式説明ではProはPlusに対して5倍または20倍のCodex利用枠を選べる。利用消費はモデル、タスクの規模・複雑さ、文脈などで変わり、週単位の制限もあり得る。**5xは開発速度5倍・5人分の作業能力を意味しない。** この計画では利用回数の固定保証や追加クレジット購入を前提にしない。出典：[OpenAI公式 Pricing](https://learn.chatgpt.com/docs/pricing)（2026-09-21確認）。

### 任せる作業と本人が確認する作業

| Codexへ依頼する作業 | 本人が確認すること |
| --- | --- |
| Logic/Context、状態機械、DTO、Validator、保存復元、境界ケースのテスト | 停止限界・鎖錠条件・単位・方向・データ所有者が仕様通りか |
| 路線・ダイヤの繰返しデータ、配置スクリプト、ログ解析 | 線形の見た目、ホーム有効長、運行時分、通しで運転した感触 |
| 既存機器へのAdapterと小さいUIの実装 | Unityの参照、更新順、Prefab、実ビルドでの動作 |
| 変更後の差分レビュー、再現手順からの不具合調査 | 再現が消えたか、他のシナリオへ影響していないか |

同じScene/Prefabを複数の作業で同時に編集しない。別の作業を走らせる場合も、共有契約を先に決め、独立したC#やテストへ範囲を限定し、統合とレビューは1件ずつ行う。

### 1回の依頼を小さくする

1件は「入力契約＋期待結果＋検証方法」を明記できる大きさにする。本人のレビュー・接続確認が30〜90分程度で終わる粒度を目安とし、毎週4〜6個の作業枠をさらに必要な範囲で分割する。大量のコードを一度に生成して週末にまとめて接続しない。

依頼例：

```text
対象：W2-02 編成全長の閉塞占有
前提：Documentation/implementation-plan-2026-11-17.md と
      Documentation/Architecture/ImplementationRules.md を確認する。
入力：先頭基準点、編成寸法、実際に通過したEdge列、閉塞範囲。
出力：占有閉塞ID集合と不正経路の診断。
条件：後退しても編成向きを反転しない。分岐跨ぎでも中間閉塞を落とさない。
変更範囲：占有Logic/Contextと関連テスト。Scene/Prefabは変更しない。
完了：3閉塞跨ぎ、境界一致、後退、履歴不足のテスト結果と変更理由を示す。
```

### 利用枠の配分

- 第1〜5週は依存関係の多い走行・保安・snapshotの実装とレビューを優先し、文書の繰返し書直しや無関係なリファクタリングに使い過ぎない。
- 単純なデータ整形・小規模コードには軽い設定、曖昧な契約・不具合調査・保安レビューには推論を厚くする設定を選ぶ。特定のモデル名に日程を依存させない。
- 毎週、利用状況と「提案のうち実際に採用できた変更」を確認する。待ち時間より本人のレビュー滞留が増えたら、同時に依頼する量を減らす。
- 利用枠に達した日は路線配置・試運転・ダイヤ入力・素材調整へ切り替える。未レビューの変更をまとめて取り込んで日程を埋めない。
- 完了報告には変更ファイル、実行したテスト、未実行の確認、残る不具合を必ず残す。Codexの「実装完了」と週末の「遊べるビルド」を分けて管理する。
